## Summary
---

The 68020 (and EC020) caches instruction fetches on-chip: 64 lines of one
longword each, direct-mapped, filled on a miss and served on a hit
without a bus cycle. Data writes never go through it. That is exactly the
situation self-modifying code depends on getting right -- a program that
pokes a new instruction word into memory and then executes it is betting
that the fetch sees the write, not a line filled earlier from the same
address.

Whether that bet pays off is controlled by CACR (bit 0 enable, bit 1
freeze, bit 2 clear one entry via CAAR, bit 3 clear everything), reached
only through the privileged `MOVEC`.

Two tests live here. `icache` asks *whether* a fetch came from the cache.
`prefetch1` asks *where the entry boundaries fall*, and it turns out the
two questions are not independent: `icache` quietly tested nothing for a
while because of an alignment accident that `prefetch1` exists to draw.

---

### How both tests are structured

Every trial runs inside the level 3 (vertical blank) handler, all twelve
of them back to back, once per frame. No trial touches COLOR00. Each one
writes its answer into a **data word of the Copper list**, and the Copper
then runs an unchanging list for the whole visible frame, moving each
stripe's word into COLOR00 when it reaches that stripe's line.

This is worth stating plainly because both tests were originally built
the other way -- a Copper-raised interrupt once per stripe, with the
handler writing COLOR00 directly -- and that design cannot be made to
work. A trial's handler genuinely writes an intermediate colour before it
writes the answer, so if the interrupt fires anywhere the beam is already
scanning a recorded line, the intermediate is exactly as visible as the
final result. Widening the margin only moves the race; it never removes
it. `icache_A1200_perstripe_irq.jpeg` in this directory is what that
looked like on a real Amiga 1200 with eight lines of slack: a black dash
at the top of every stripe. Worse, the handler's runtime *depends on the
cache behaviour under test*, so it is different for every stripe -- there
is no margin that is correct for all twelve.

Running in vertical blank removes the question rather than tuning it.
There is no settle margin in either test now, no `SETTLELINES`, and
nothing to re-record when CPU timing shifts by a few cycles.

Each stripe's Copper block is a fixed 16 bytes, generated by `rept`, and
the handler walks it in fixed strides instead of carrying a table of
twelve pointers. An assembly-time assertion ties the stride to the block
so the two cannot silently drift apart.

MOVEC is privileged, and this suite's start-up code is not in supervisor
mode by the time MAIN gets control -- a bare `movec` there takes a
privilege violation, confirmed by installing a private vector $20 handler
and watching it fire. A hardware interrupt always enters supervisor mode
regardless of what it interrupts, which is why every MOVEC in both tests
lives in the handler.

### icache

Two colours. Yellow means the CPU executed the instruction that was just
self-modified; black means it executed the one that was there before.

One stub, used twelve times:

```
stub:  move.w  #$0000,(a3)     ; a3 -> a word of the Copper list
       rts
```

Opcode and immediate share one cache longword, so one fetch decides the
whole instruction. Each stripe is a self-contained trial:

```
PRIME   poke the stub's immediate to black, flush the whole cache
        (CACR bit 3) enabled and unfrozen, call the stub -- a
        guaranteed miss that fetches black fresh and caches that fetch.

TEST    apply this stripe's CACR value, poke the immediate to yellow,
        call the stub again.
```

If the test's CACR value left the primed line valid, the second call hits
it and yellow never took effect -- black shows. If it invalidated that
line (or the cache is off outright), the call misses, fetches yellow
fresh, and yellow shows. Six CACR values, repeated twice:

```
$0000  off                        miss regardless:                 yellow
$0001  on, unchanged from priming  still valid, hits:               black
$0005  on, CE (invalidate)         invalidated, miss:               yellow
$0003  on, frozen, no invalidate   still valid, hits:               black
$0007  on, frozen + CE             invalidated + frozen, stays miss: yellow
$0009  on, C (flush everything)    invalidated, miss:               yellow
```

Recorded result: yellow, black, yellow, black, yellow, yellow, twice.

CAAR is set once per frame to the stub's own address -- every "clear
entry" in this test means the same thing.

#### The stub must be longword aligned

This is not a detail. `move.w #imm,(a3)` is two words, opcode and
immediate, and only if they share one longword does a single cache entry
cover both -- only then does "invalidate the stub's line" invalidate the
whole instruction.

Put the stub on an odd word and the opcode lands at the end of one
longword while the immediate -- the word the test actually rewrites --
lands at the start of the next:

```
$70248 = [ rte   , opcode ]   idx 18   <- what CAAR = stub invalidates
$7024C = [ $BEEF , rts    ]   idx 19   <- where the immediate lives
```

A CE aimed at CAAR = stub then clears the opcode's entry and leaves the
stale immediate being served from the entry beside it. Both CE stripes
and both CE+freeze stripes come out black, and the picture looks exactly
like a CPU that ignores CACR bit 2.

An earlier variant of this test shipped in that state, and a real A1200
reproduced it faithfully -- `icache_A1200_oddword_stub.jpeg` is the
photograph, yellow / black / black / black / black / yellow, matching
vAmiga stripe for stripe. That agreement is worth remembering for what it
is not: hardware and emulator agreeing says nothing about whether either
one is answering the question you meant to ask. The stub is now pinned by
a `cnop 0,4` placed at the head of the block, so its alignment is fixed
independently of how the code above it changes length.

#### One layout constraint

The cache is direct-mapped on address bits 7..2, so any two addresses
exactly 256 bytes apart share an entry. Between PRIME and TEST the
handler executes its own instructions, and if any of them aliased the
stub's entry it would evict the line the trial depends on -- the CE
stripes would still be yellow, but so would ON and FREEZE, for entirely
the wrong reason. The stub and the handler are laid out adjacently and
the span is asserted at assembly time to be under 256 bytes, which makes
that impossible by construction rather than by inspection of a link map
that changes every time the source does.

#### `move.w #$0000,(a3)` is not the instruction you wrote

vasm quietly rewrites a zero immediate into the 2-byte `clr.w (a3)` -- no
immediate word at all -- while any non-zero immediate keeps the full
4-byte encoding. This test's poke writes into what it assumes is the
second word of the stub; with a `$0000` placeholder that word does not
exist and the poke lands on the `rts`. The compiled-in placeholder is
`$BEEF` for exactly this reason. It is only ever visible for the very
first fetch of the very first frame, before the first prime, but it has
to be non-zero regardless. This would bite on real hardware identically;
it is not an emulator issue.

### prefetch1

`icache` asks whether a fetch came from the cache. `prefetch1` asks which
instructions share an entry with which, and answers by counting.

It grew out of this passage in the 68020 user manual:

> "The MC68020 always prefetches long words. When an instruction
> prefetch falls on an odd word boundary (e.g., due to a branch to an
> odd word location), the MC68020 will read the even word associated
> with the long word base address at the same time as (32-bit memory)
> or before (8- or 16-bit memory) the odd word is read. [...]"

It is easy to read that as "a misaligned fetch fills two cache lines". It
does not, and the distinction is the whole point. A cache entry *is* one
longword, tagged by the longword address and indexed by bits 7..2; bits
1..0 play no part in the lookup. Fetching the word at $1006 and fetching
the word at $1004 are the same lookup, of the same single entry, covering
the same single longword. One fetch, one entry, always.

What the passage is about is the *bus*. On a 16-bit port, fetching only
the odd word would leave the entry half filled, and a half-filled entry
cannot be marked valid, so the CPU reads the even word too even though
nobody asked for it. The visible consequence is not two lines. It is that
**the entry point's alignment decides how the instruction stream gets
carved into entries**: enter on an even word and they come out `{i0,i1}
{i2,i3} ...`, enter one word later and they come out `{--,i0} {i1,i2}
...`, with the first entry carrying only one instruction of the stream
because the other half of it is the word in front of the entry point.

#### How it is measured

Two identical chains of eleven `addq.w #1,d0` followed by an `rts`.
`chainA` starts on an odd word; `chainB` starts longword-aligned. One
stripe is one trial, and each is self-contained:

```
RESTORE  write addq.w #1,d0 over all eleven words of the chain
PRIME    CACR = $0009 (flush all, on, unfrozen), call the chain --
         every longword of it is fetched from memory and cached
BLANK    write nop over all eleven words, so anything fetched from
         memory from here on counts for nothing
PUNCH    CAAR = one chosen longword of the chain, CACR = $0007
         (on, CE, frozen): invalidate exactly that entry, and freeze
         so it cannot refill
RUN      d0 = 0, call the chain again
```

Every instruction whose entry is still valid is served from the cache as
the `addq` it was primed with. Only the instructions inside the punched
longword go to memory, where they are now `nop`s. So

```
d0 = 11 - (number of chain instructions in the punched longword)
```

and d0 indexes a sixteen-entry palette directly -- the bar colour *is*
the answer, read off a register. Entry 9 is blue, entry 10 is yellow, and
the other fourteen are deliberately nothing like either, so a wrong
result is a wrong colour rather than a subtly different one.

#### Recorded result

```
chainA (odd-word entry)      chainB (aligned entry)
 1  yellow  d0 = 10           7  blue    d0 = 9
 2  blue    d0 = 9            8  blue    d0 = 9
 3  blue    d0 = 9            9  blue    d0 = 9
 4  blue    d0 = 9           10  blue    d0 = 9
 5  blue    d0 = 9           11  blue    d0 = 9
 6  blue    d0 = 9           12  yellow  d0 = 10
```

One yellow bar at the top of the first group and one at the bottom of the
second, blue everywhere else. The odd bar out marks the partial longword,
and it moves from one end of the chain to the other purely because the
entry point moved by one word. If the cache were word-granular instead,
punching one "longword" would cost exactly one instruction everywhere and
all twelve bars would be yellow.

**Confirmed on hardware.** `prefetch1_A1200.jpeg` is a real Amiga 1200
running this disk, and it matches the recorded reference stripe for
stripe. Two things follow beyond the alignment claim itself: the JSR fix
below is validated by hardware (without it vAmiga answers 9 where the
A1200 answers 10), and blue meaning `d0 = 9` proves the A1200 really is
serving instruction fetches from cache for code in chip RAM.

#### The bug it found

The first recorded picture was not that one: every bar of the first group
came out one colour short. Tracing showed Moira's `execJsr` fetching the
word at the jump target with a plain bus read

```cpp
queue.irc = (u16)read<C, AddrSpace::PROG, Word>(ea);
prefetch<C>();
```

on every core. That is right for the 68000, which has no cache to
consult, and wrong for the 68020: the first instruction word of every JSR
target was fetched from memory whatever the cache held, so self-modifying
code entered through a JSR always saw the fresh word. `JMP`, `BSR`,
`Bcc`, `DBcc`, `RTS` and `RTR` all went through `fullPrefetch` already.
`JSR` was the only one that did not.

`icache` never caught this and could not have: its entire self-modified
instruction -- opcode word and immediate word alike -- is meant to live in
one longword, and the immediate still came from the cache, so its answers
were right for the wrong reason. `prefetch1` catches it because chainA's
entry point is an odd word, which makes the target word the *last* word
of its longword: the bypassed fetch is then the only access that longword
ever gets, and its whole contribution to the count disappears.

The fix routes JSR through `fullPrefetch<C>()`, which also clears the
instruction latch -- the latch must not answer for a longword the jump has
just left behind.

#### The same layout constraint

Between PRIME and RUN the handler runs its own BLANK loop and two MOVECs,
and if any of that aliased a chain longword it would evict the very entry
the trial depends on, and the count would come out low for reasons that
have nothing to do with alignment. The chains and the handler are laid
out adjacently and the whole span is asserted under 256 bytes.

### cacheflush

A cache line filled immediately behind a **straddling `movec`** does not
survive the call that filled it. Nothing in the 68020 documentation
predicts this; it was found by comparing `icache` against a real Amiga
1200 and narrowed over thirteen probe disks.

#### The behaviour

A cache entry covers exactly one longword-aligned longword, so one fetch
can never fill two entries. But a four-byte instruction at an odd word
*spans* two entries and needs two fetches. `movec Dn,cacr` is four bytes,
so it straddles exactly when it sits on an odd word.

On a real 68EC020 a line filled by a JSR's target fetch fails to stay
valid when **both**: nothing separates the CACR write that cleared the
cache from the JSR, *and* that `movec` straddles a longword boundary.

It is the **flushing `movec`'s** alignment that decides this, not the
JSR's — the point the test's last two groups exist to establish, since
`movec` and an adjacent `jsr` are both four bytes and therefore always
share alignment when nothing separates them. JSR's three lengths break
the tie:

```
                movec        JSR form                 result
stripes 13-15   aligned      jsr (d16,PC)  4 bytes    black
stripes 16-18   straddles    jsr (d16,PC)  4 bytes    YELLOW
stripes 19-21   ALIGNED      jsr (xxx).L   6 bytes    black    <- decisive
stripes 22-24   STRADDLES    jsr (An)      2 bytes    YELLOW   <- decisive
```

A JSR that *cannot* straddle still loses the line behind a straddling
`movec`; one that *always* straddles keeps it behind an aligned one.

The likely reading is that a straddling `movec` must fetch the following
longword to complete itself, so the words the next instruction needs are
already in the pipe — and already cached — when the flush runs. A real
three-word 68020 prefetch pipe would probably produce this by itself.
Moira's queue is two words wide (`irc`, `ird`), the 68000 shape, for
every core, so `execJsr` stands in for it with an explicit flag. That is
a placeholder, not a model: it covers JSR only, where the underlying
effect is unlikely to be JSR-specific.

Confirmed against an A1200 (`cacheflush_A1200.jpeg`).

#### How it was found, and what that cost

`icache` originally raised an interrupt per stripe and wrote COLOR00 from
the handler. On an A1200 every stripe came out yellow where vAmiga said
four should be black. Eliminating the obvious suspects took eight
hardware round trips and every one was wrong:

```
CPU speed              cleared   4x OVERCLOCKING sweep, bit-identical
cache semantics        cleared   the VBlank icache matches hardware
stub alignment         cleared   both designs longword-aligned
mid-frame interrupts   cleared   a single mid-frame trial keeps its line
COLOR00 vs chip RAM    cleared   still yellow writing to RAM
CACR table walk        cleared   every loaded CACR value verified correct
handler shape          cleared   movem and register source irrelevant
raster position        cleared   same lines, opposite results
trigger count          cleared   6 and 12 triggers behave identically
line aliasing          cleared   computed; no collision in any case
```

Each of those "cleared" because every structural edit moved the code by
two or four bytes as a side effect, flipping the alignment of the `movec`
underneath the variable being tested. Four things worth keeping:

**Bisect by editing the smallest thing that can possibly matter.** The
decisive step was two builds differing only by 66 bytes of padding that
nothing executes.

**Photographs of a CRT cannot be trusted for colour.** This monitor
renders `$006` with a blue channel of 235 where linear predicts 102. One
probe was misread as "all black" when it was `$444` grey, and a
conclusion drawn from it had to be retracted. Every test here now carries
reference swatches so an ambiguous stripe can be compared against known
ones in the same frame at the same exposure.

**A rule that fits every observation can still be wrong.** Two successive
rules fitted all data at the time — one keyed on the priming JSR's
alignment (nine handlers out of nine) — and each was refuted by the next
disk. Both had been derived after the fact.

**Confounds hide in what you changed to vary something else.** The JSR
rule survived a predictive test and was still wrong: the `nop` used to
move the JSR off alignment had also moved the `movec`. Only instructions
of *different lengths* could separate them.
